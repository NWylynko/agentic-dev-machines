# Project notes

- Read `README.md` for the quick start, `docs/installation.md` for install/update behavior, `docs/operations.md` for day-to-day commands, Herdr ownership, and verification, `docs/product-requirements.md` for design requirements, and `docs/implementation-contract.md` for the implemented API. Storage backend, the node-failure loss window, and live Herdr installation remain open.
- `adm` is the Rust CLI. The runner and terminal are the npm workspaces `@adm/runner` and `@adm/terminal`. Repository catalog code is `packages/repositories`. The workspace image is `image/Dockerfile` (`adm-dev:0.1.0`).
- Repository code is MIT licensed in `LICENSE`; release archives and the workspace image include that license.
- Tests: `cargo test`, `npm test`, and `npm run test:repositories`. The repository test needs `/dev/fuse` and `artifact-fs` on `PATH` (pin in `packages/repositories/ARTIFACTFS`). It skips without `/dev/fuse` and fails if the binary is missing while FUSE is present.
- `.github/workflows/build.yml` verifies the CLI, runner, and terminal, then publishes `linux/amd64` `adm`, `adm-repositories`, a complete runtime archive, and the workspace image to GHCR. Successful `main` builds automatically publish a `sha-<commit>` GitHub release and mark it latest after image and binary checks pass. Optional `v*` tags publish pinned releases without promoting latest. Published assets are preserved on reruns; stale main builds are not promoted. The verify job runs `npm run test:publish`, which executes the workflow's release step against a fixture GitHub boundary. Markdown-only pushes and pull requests skip the workflow. FUSE tests stay outside this workflow. Installed CLIs discover the matching compiled runtime beside their executable; `--project-dir` / `ADM_PROJECT_DIR` can select a development checkout. Third-party Pi dependencies must keep their worker/WASM assets, so release packaging bundles only local TypeScript and installs pinned external production dependencies.
- `install.sh` uses checksum-addressed immutable releases under `$XDG_DATA_HOME/adm/install` and stable commands in `$HOME/.local/bin`. It preserves state/config, validates before switching, and offers `adm setup` on first interactive installation. `npm run test:install` tests the shell installer with release fixtures; `cargo build --bin adm && npm run test:release` verifies an actual runtime archive without checkout paths. Its default download follows the latest successful `main` release; version tags remain optional.
- `adm setup` saves only nonsecret image/StorageClass/model defaults to `$XDG_CONFIG_HOME/adm/config.json` and optionally offers pinned Pi login and a systemd user service. Explicit flags win; `--no-agent` disables agents even with a model default. `adm serve` execs Node on Unix so supervision signals reach the runner. Do not store API keys in ADM config/services or import shell keys into systemd.
- `cargo clippy --all-targets -- -D warnings` and `npm run check` check the implementations. `npm run test:image -- IMAGE` runs isolated unprivileged Docker/Git/Chromium checks. `ADM_LIVE_CLUSTER=1 npm run test:cluster-contract` checks real owned namespace lifecycle and server-side manifest validation. The full `test:cluster` additionally needs `ADM_LIVE_IMAGE` cached on every schedulable node; it never installs node helpers.
- Agent creation requires a default model configured by `adm setup` or explicit `--model PROVIDER/MODEL_ID`, or `--no-agent` for a shell-only workspace. The lazy catalog is opt-in through `--catalog`; ordinary workspaces have a writable `/repos` without a FUSE sidecar.
- Provider failures persist in runner status/history. `/resume` is explicit and deduplicated; after tools have run, reconcile their effects with a deliberate follow-up. Do not add provider/billing or environment fallback.
- `adm herdr watch --socket "$HERDR_SOCKET_PATH"` runs inside the owning Herdr session and journals received explicit close events before cleanup. Never infer deletion from missing spaces or a lost connection. The current Herdr API has no replay cursor for missed events; supervise the watcher and keep this limitation visible.
- The target is a homelab CLI/workspace service integrated with Herdr and Kubernetes. Workspace identity must be independent of the current runtime and physical node.
- Confirmed persistence scope: repository work and agent history; installed tools are ephemeral or supplied by the base image. Some recent work loss after rare unexpected node failure is acceptable; the exact window is unchosen.
- Every development workspace has private writable files and Git state, regardless of branch names. Share immutable upstream data only. Coding agents have no access to other workspaces; bots may use explicitly permitted monitoring/prompting interfaces without repository, shell, or general cross-workspace access.
- Agents must execute unattended independently of SSH, CLI, and terminal connections. SSH clients connect to Herdr on a long-running Debian management host.
- Manual Herdr space removal destroys its runtime and private files and cancels its owned agents, goals, loops, and pending work. Recovery must not recreate deliberately deleted workspaces. Conversation retention remains open; configurability is an acceptable proposal.
- User-facing coding and bot conversations belong in Herdr with a Pi-style terminal interface. Browser automation and access to development sites/ports from client laptops are required.
- Bots are a separate non-coding role: no repository access or coding tools, including indirectly through Code Mode. They can monitor/prompt explicitly permitted coding agents and maintain durable goals/loops. Bot-to-space and bot-to-agent assignments remain open.
- Bot model output is hidden by default; only explicit `sendMessage` calls publish AI-authored messages in its terminal conversation. Keep inspectable diagnostics separate from chat delivery.
- Keep providers/auth configurable; account compatibility, numeric budgets, and migration are not settled. No silent provider/billing fallback.
- Lazy GitHub repository access and storage efficiency on storage-constrained nodes remain goals. The storage backend is still unchosen. The runner is Pi Durable 1.2.0 on the management host, distinct from ordinary Pi session files. Coding tools run in the workspace container.
- `docs/pi-durable-research.md` records the 1.2.0 findings. The terminal is an HTTP client, not native Pi RPC. Harness close and ordinary abort are not workspace destruction. SQLite WAL still needs a compatible filesystem and one owner; it is not a cross-node durability proof.
- Preserve the distinction between requirements and proposals. Do not turn candidate technologies or command syntax into settled decisions without evidence.
- Do not claim transparent process recovery or filesystem durability that has not been demonstrated end to end.
- Keep implementations simple, colocate feature code, and write end-to-end tests first for behavior changes. Verify the expected failure before implementing a change, and keep failures visible in status and logs.
- Keep secrets in Infisical and inject API keys into the runner process; commit schema only. Never store real keys in repository env files, ADM config, or service units.
