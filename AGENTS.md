# Project notes

- Implemented runtime boundary (2026-10-16): coding and bot agents run inside their own workspace Pods. The management host is a Kubernetes/lifecycle access plane; it does not run agent harnesses or provider sessions. Workspace identity and repository/history data belong to the workspace namespace and PVC. Each Pod receives only its own projected `adm-lifecycle` identity; the controller never forwards its broad lifecycle credential into a workspace.
- Current verification and live image-distribution/Herdr prerequisites are recorded in `docs/validation-2026-10-17.md`. Fixture/container evidence does not establish current-image Kubernetes rollout or sudden-node-loss durability.
- `adm destroy NAME` returns its durable lifecycle operation receipt after admission; `--wait` observes confirmed cleanup and returns the deleted workspace record. Repeating destroy resumes the original operation, including after service restart; immutable workspace IDs protect reused names.
- Interactive plain/managed workspace shells run zsh with pinned Oh My Zsh. Editable `.zshrc` and history live in `/workspace/.adm/zsh` and are seeded once; explicit shell/exec command arguments retain their semantics. GitHub HTTPS pushes use only the workspace's explicit `GH_TOKEN` through the image's GitHub-scoped helper.
- All coding and bot execution belongs in workspace Pods; the host is an access plane only. Bots broadly control live coding-agent lifecycles through authenticated runtime APIs. Lifecycle admission verifies the caller's current source Pod UID and runtime lease and permits bot-to-coding control by immutable workspace ID; it grants no repository, shell, or general cross-workspace access. Agents have unattended root/sudo inside their own Pods.
- Early-alpha policy (2026-10-16): prioritize a simple fresh implementation. No old-data/configuration migration, legacy upgrade paths, or backwards-compatibility layers are required. Keep persistence, restart recovery, and deletion correctness for the new design.
- Design investigation and implementation boundaries are in `docs/todo-investigation-2026-10-16.md` and its linked runtime/management/CLI research notes. TASK-22 owns Pod runtime/routing; TASK-47 owns shared in-cluster lifecycle operations. TASK-48 is merged into TASK-22 and TASK-49 is canceled. The new runtime path is implemented, but full installation and end-to-end cluster validation remain open.
- Read `README.md` for the quick start, `docs/installation.md` for install/update behavior, `docs/operations.md` for day-to-day commands, Herdr ownership, and verification, `docs/product-requirements.md` for design requirements, and `docs/implementation-contract.md` for the implemented API. Storage backend, the node-failure loss window, and live Herdr installation remain open.
- `adm` is the Rust CLI. The runner and terminal are the npm workspaces `@adm/runner` and `@adm/terminal`. Repository catalog code is `packages/repositories`. The workspace image is `image/Dockerfile` (`adm-dev:0.1.0`).
- Repository code is MIT licensed in `LICENSE`; release archives and the workspace image include that license.
- Tests: `cargo test`, `npm test`, and `npm run test:repositories`. CLI shell fixtures need zsh on the test host; CI installs it in both verification and release runners. Image smoke tests also need host npm dependencies for their esbuild fixture, independently of the Docker build's dependencies. The repository test needs `/dev/fuse` and `artifact-fs` on `PATH` (pin in `packages/repositories/ARTIFACTFS`). It skips without `/dev/fuse` and fails if the binary is missing while FUSE is present.
- `.github/workflows/build.yml` verifies the CLI, runner, and terminal, then publishes `linux/amd64` `adm`, `adm-repositories`, a complete runtime archive, and the workspace image to GHCR. Successful `main` builds automatically publish a `sha-<commit>` GitHub release and mark it latest after image and binary checks pass. Optional `v*` tags publish pinned releases without promoting latest. Published assets are preserved on reruns; stale main builds are not promoted. The verify job runs `npm run test:publish`, which executes the workflow's release step against a fixture GitHub boundary. Markdown-only pushes and pull requests skip the workflow. FUSE tests stay outside this workflow. Installed CLIs discover the matching compiled runtime beside their executable; `--project-dir` / `ADM_PROJECT_DIR` can select a development checkout. Third-party Pi dependencies must keep their worker/WASM assets, so release packaging bundles only local TypeScript and installs pinned external production dependencies.
- `install.sh` uses checksum-addressed immutable releases under `$XDG_DATA_HOME/adm/install` and stable commands in `$HOME/.local/bin`. It preserves state/config, validates before switching, and offers `adm setup` on first interactive installation. `npm run test:install` tests the shell installer with release fixtures; `cargo build --bin adm && npm run test:release` verifies an actual runtime archive without checkout paths. Its default download follows the latest successful `main` release; version tags remain optional.
- `adm setup` saves nonsecret image/StorageClass/model defaults to `$XDG_CONFIG_HOME/adm/config.json`; credentials are entered in the selected workspace with `adm login NAME`. Explicit flags win. Every workspace starts a durable agent, and `/model` in `adm attach` selects its model when no default was seeded. `adm start`, `adm serve`, and `adm stop` do not start a host agent runner. Do not store API keys in ADM config or service units.
- `adm shell NAME --manage` uses a short-lived local relay into the selected workspace Pod and exposes only status, history, prompt, and abort inside that shell. The ordinary shell path starts no relay; closing a managed shell leaves the agent running.
- The CLI uses host-side kubeconfig credentials only for lifecycle and scoped Pod access. Workspace registration stores the selected kubeconfig path list in the Pod runtime metadata; kubeconfig contents stay on the host. `adm reconnect NAME --kubeconfig PATHS` repairs that binding after namespace ownership verification while preserving the workspace ID, files, and history.
- `adm list` reads the lifecycle directory and joins bounded live activity by immutable workspace ID; unavailable Pod/runtime data has an explicit cause. Selected `adm status` separates persisted phase, agent configuration/activity, and runtime readiness, including namespace, model, resources, node, and failure causes. Live status collection uses a short-lived TokenRequest bound to the exact target Pod and sends that token only to that Pod.
- `cargo clippy --all-targets -- -D warnings` and `npm run check` check the implementations. `npm run test:image -- IMAGE` runs isolated Docker/Git/Chromium checks. `ADM_LIVE_CLUSTER=1 npm run test:cluster-contract` requires `ADM_LIFECYCLE_URL` and `ADM_LIFECYCLE_TOKEN_FILE` and checks real owned namespace lifecycle and server-side manifest validation. The full `test:cluster` also requires `ADM_LIVE_IMAGE` cached on every schedulable node; it never installs node helpers. A disposable live Kubernetes permission check verified target-bound TokenRequest/TokenReview, Pod exec, and namespace retry authorization against an older cached image. It did not validate the new runtime image or a complete installation.
- Workspace creation always registers the durable agent in its Pod. A default model from `adm setup` or explicit `--model PROVIDER/MODEL_ID` seeds a new conversation; without one, the agent waits in `needs_model` until `/model` selection. The Pod runtime exposes model metadata at `GET /v1/workspaces/:id/models` and persists changes through `PUT /v1/workspaces/:id/model`; Durable's conversation model is authoritative. The lazy catalog is opt-in through `--catalog`; ordinary workspaces have a writable `/repos` without a FUSE sidecar.
- `adm create --repo OWNER/REPO` prepares one public GitHub checkout at `/repos/OWNER/REPO`, then registers the agent with that persisted cwd. It uses the ordinary private workspace volume, never enables the lazy catalog, and does not configure private-repository authentication. Creation retries preserve a published checkout and local edits.
- Provider failures persist in Pod runtime status/history. Lease/fence loss closes active workspace work, rejects new writes, logs the failure, and makes health fail so Kubernetes restarts the Pod; no provider/billing or environment fallback is allowed. `/resume` is explicit and deduplicated; after tools have run, reconcile their effects with a deliberate follow-up.
- `adm herdr watch --socket "$HERDR_SOCKET_PATH"` runs inside the owning Herdr session and journals received explicit close events before cleanup. Never infer deletion from missing spaces or a lost connection. The current Herdr API has no replay cursor for missed events; supervise the watcher and keep this limitation visible.
- The target is a homelab CLI/workspace service integrated with Herdr and Kubernetes. Workspace identity must be independent of the current runtime and physical node.
- Confirmed persistence scope: repository work and agent history; installed tools are ephemeral or supplied by the base image. Some recent work loss after rare unexpected node failure is acceptable; the exact window is unchosen.
- Every workspace has private writable files and Git state, regardless of branch names. Share immutable upstream data only. Coding agents have no access to other workspaces; bots may inspect and control coding-agent lifecycle/runtime APIs by immutable ID, without repository, shell, or general cross-workspace access. Workspace containers include nano and passwordless sudo by default, with ordinary commands at UID 1000 and CHOWN, DAC_OVERRIDE, FOWNER, SETGID, and SETUID capabilities scoped to their own Pod. OS package installs are lost on Pod replacement.
- Agents execute unattended independently of SSH, CLI, and terminal connections. SSH clients connect to Herdr on a long-running Debian management host. Destroy marks the workspace deleting before namespace cleanup; deleted work must not be recreated by restart recovery.
- Manual Herdr space removal tombstones its workspace, deletes its runtime namespace and private files, and cancels its owned agents, goals, loops, and pending work. Recovery must not recreate deliberately deleted workspaces. Conversation retention remains open; configurability is an acceptable proposal.
- User-facing coding and bot conversations belong in Herdr with a Pi-style terminal interface. Browser automation and access to development sites/ports from client laptops are required.
- Bots are a separate non-coding role: no repository access or coding tools, including indirectly through Code Mode. They broadly control live coding agents through authenticated lifecycle/runtime APIs and maintain durable goals/loops. Bot-to-space assignments remain open.
- Bot model output is hidden by default; only explicit `sendMessage` calls publish AI-authored messages in its terminal conversation. Keep inspectable diagnostics separate from chat delivery.
- New bots with a selected model begin one durable identity/purpose setup turn. Bot profiles survive restart; legacy conversations without a profile stay unchanged. CLI `--mcp-config` grants exact stdio tools and injected environment references to the owning workspace runtime, never secret values or ambient provider credentials. MCP calls must honor cancellation and close with their workspace.
- Keep providers/auth configurable; provider account support and numeric budgets are not settled. No silent provider/billing fallback. Legacy data/configuration migration is out of scope during early alpha.
- Lazy GitHub repository access and storage efficiency on storage-constrained nodes remain goals. The storage backend and exact node-failure loss window are still unchosen. The runner uses Pi Durable 1.2.0 inside the workspace Pod, distinct from ordinary Pi session files. Coding tools and provider sessions run in the same owning Pod. The replacement image has been built and smoke-tested locally, but has not been validated end to end across the cluster; live Herdr installation and real provider sessions remain unverified.
- `docs/pi-durable-research.md` records the 1.2.0 findings. The terminal uses Pi's Markdown and multiline editor over HTTP/SSE; it does not launch native Pi InteractiveMode or own another session. Harness close and ordinary abort are not workspace destruction. SQLite WAL still needs a compatible filesystem and one owner; it is not a cross-node durability proof.
- Preserve the distinction between requirements and proposals. Do not turn candidate technologies or command syntax into settled decisions without evidence.
- Do not claim transparent process recovery or filesystem durability that has not been demonstrated end to end.
- Keep implementations simple, colocate feature code, and write end-to-end tests first for behavior changes. Verify the expected failure before implementing a change, and keep failures visible in status and logs.
- Use the operator's chosen secret source and inject credentials only into the runtime that needs them; commit schema only. Never store real keys in repository env files, ADM config, or service units.
