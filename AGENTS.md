# Project notes

- Herdr pane routing (2026-10-23, TASK-76): stock Herdr 0.9 reads `config.toml` only at server start or `herdr server reload-config`; editing `terminal.default_shell` alone leaves new panes on the old shell (verified in a throwaway `herdr --session NAME server` with `HERDR_CONFIG_PATH`). ADM bind/disable now reload and fail loudly if it is not `applied`. `workspace.create` env reaches only the root pane, not later splits. Herdr closes a pane the moment its shell exits, so a failed routed shell holds the pane with `Press Enter to close this pane.` when stdin is a terminal.
- `adm list` latency (2026-10-23, TASK-67): live per-row cost was a TokenRequest (~0.1 s incl. its Lease check) plus the runner's `runtime/authorize` callback (~0.38 s: every lifecycle kubectl call is preceded by a `get lease` Lease verification, ~55 ms each, plus TokenReview, `get pods -A`, SQLite opens), on top of `status()` (~0.25 s). Client overhead (secret read + port-forward + first request) is ~0.3 s. Runtime status is now unauthenticated (NetworkPolicy already limits port 7432 to lifecycle/bots), all Pods are read at once, and collection is bounded at 1 s. Timing harness scripts used: read-only `kubectl exec` into `deploy/adm-lifecycle` timing curl/kubectl, and `adm list` with temp XDG dirs.

- Saved workspace image follows releases (2026-10-23, TASK-62): `adm setup` saves the release IMAGE as an explicit `config.image`, and `adm create` uses it, so after `adm update` new workspaces kept the setup-time runner (live: controller `sha-ad41c466706e`, every workspace incl. freshly recreated ones on `sha-9b38a7023cc3`, so the runtime-status fix never ran). `update_services` now calls `advance_saved_release_image`: a saved image in the release's repository moves to the new release IMAGE; another repository is kept. Covered in `tests/release.test.mjs` (run with `ADM_RELEASE_TEST_ADM=<built adm>`). When a fix lives in the runner, check the workspace Pod image, not just the controller.

- Failed create retries (2026-10-20, TASK-73): an ordinary same-name/same-spec `adm create` admits a new operation against the retained workspace row (`ON CONFLICT(id) DO NOTHING`), preserving its immutable ID, namespace/PVC, published checkout and original `creation_operation_id`. Admission rejects another create while one is accepted/running and identifies that operation, including when replaying an older failed ID. Restart queues only the latest failed create attempt per workspace; older failure receipts remain inspectable and explicitly replayable. `create_persisted` rejects deleting/deleted identities and a changed same-name identity before provisioning. Public CLI/Git fixtures cover retry failures, edit preservation, changed specs, overlap and deleted-name reuse; the lifecycle HTTP fixture covers retry recovery after restart.

- Runtime fencing shutdown (2026-10-20): `assertActive` publishes ownership loss and starts `fenceLost` without awaiting shutdown. Shutdown drains workspace admissions and Durable work, so awaiting it inside their own authority check deadlocks the operation and its HTTP response (CI reported a five-minute `UND_ERR_HEADERS_TIMEOUT`). The HTTP regression revokes ownership on the input admission check and verifies prompt rejection, failed health, and clean process shutdown.

- Repository branches (2026-10-20, TASK-66): `adm create --repo OWNER/REPO --branch BRANCH [--base REF]` switches branches in the Pod staging checkout before publication. Existing `origin/BRANCH` tracks the remote; a new branch starts at `refs/remotes/origin/HEAD` or an explicit commit-resolving Git ref (e.g. `origin/release`) and remains local. Branch/base persist in Workspace/CreateIntent and retry equality. `--base` requires `--branch`; both require `--repo`. Git validates names in the Pod so clients gain no Git dependency. Same-spec retries retain identity and published edits, with or without the original `--operation-id` (TASK-73). Public CLI local Git fixtures and the bot HTTP test cover this path.

- Bot live attach (2026-10-20): explicit `sendMessage` records project to Pi custom `message_start` followed by `message_end`; Pi only adds custom messages on start. Public bot SSE publishes only `{type:"activity",active:boolean}` from Durable's run snapshot/start/end, keeping model/tool content private and remaining busy across private tool rounds. Native attach retains activity received before its UI subscription, so reconnecting mid-run shows Working; success, provider failure, and abort settle it. `packages/terminal/test/bot-live.test.ts` exercises real native PTYs, onboarding, live replies, cursor replay, and a gated host-granted MCP tool without provider calls.
- Runtime status (2026-10-19): the runner's `GET .../runtime-status` (what `adm list`, `adm status` and bot `listAgents` collect concurrently under the lifecycle's 1 s bound, unauthenticated since TASK-67) reads only Durable activity and the conversation's own model via `Workspace.conversationSelectedModel()`. Never route it through `modelCatalog()`: that issues shared provider catalogue requests through lifecycle/provider-auth and took ~4 s per read live (TASK-62). Lifecycle collection causes format reqwest errors with `{:#}` of `anyhow::Error::new(error)` so the source chain (`operation timed out`, refused, DNS) is visible. Tests: `runtime status answers ... while the shared provider catalogue is slow` (runner) and the `runtime-status-hold` flag in `tests/lifecycle.rs`.

- Native attach integration (2026-10-19): the CLI runs pinned upstream Pi InteractiveMode through reproducibly patched remote ports, projecting the existing Durable conversation. - Saved messages in native attach (2026-10-20): every saved Durable message reaches the terminal twice, as live `message_start`/`message_end {entry}` (Durable also live-starts saved user/unstreamed messages) and as a history event, in no guaranteed order. Pi 1.2.0's `agent_end` (mapped from live `turn_end`) deletes an unfinished streaming component, and its `message_end` only finishes an existing one. `DurableInteractiveRuntime.showSavedMessage` therefore shows each entry id once, from whichever channel is first: it finishes Pi's streaming component if there is one, otherwise emits `message_start` + `message_end` (reuse it for TASK-68's bot messages). `savedEntriesShown` is cleared exactly when a reconnect re-renders the session's records (TASK-71). The PTY test emulates the screen with `@xterm/headless` (200 rows: Pi redraws its chat inside the viewport, not into scrollback), because raw PTY output keeps text Pi later removed.
- Cache warming (2026-10-19): workspace settings persist `off`, `streaming`, or `idle`; the owning runtime reuses Pi's pinned warmer with the actual provider request, one-token refresh cap, lease checks and recorded Durable usage. - Implemented trust-gated Pi extension bridge (2026-10-19): trusted coding workspace extensions load inside their owning runner Pod. Registered tools execute through the existing Durable registry; `context`, `tool_call`, and `tool_result` hooks affect the existing provider/tool path. Commands and keyboard shortcuts execute in that same runtime over typed HTTP/SSE events for supported dialogs and UI updates. Conversation-scoped Durable request tombstones prevent a command from repeating after retry or restart; at most 128 operation event histories are retained, with 256 events each, and older streams return 410 while their deduplication tombstones remain. On restart, accepted operations become visibly interrupted and are never rerun. Project extension code stays inert until persisted project trust is active; bots cannot inspect or activate it. Other hooks, CLI flags, custom widgets, and unsupported Pi UI/context methods fail visibly or appear in diagnostics. Arbitrary extension JavaScript never runs on the client.
