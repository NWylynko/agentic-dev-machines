## Confirmed product direction

- All agent execution belongs in workspace pods; the host is an access plane ([TASK-22](https://linear.app/wylynko/issue/TASK-22)).
- Bots broadly control coding agents across the installation, including creation, configuration/model selection, and destruction. Individual supervision grants and routine human approval are superseded.
- Agents and humans have unattended sudo/root authority inside their own workspace container. Separate restricted agent accounts and command approval are superseded. Other workspaces' private files and host/cluster administration remain outside this authority.

## TASK-36: the missing feature is a lifecycle interface, not just discovery

The current bot registry has exactly `saveGoal`, `saveLoop`, `saveProfile`, `listAgents`, `sendMessage`, `monitorAgent`, `promptAgent`, and `codemode`. An isolated real runner probe confirmed this registry. Only the last three supervision tools operate on coding agents; the scheduling tools address the bot's own conversation. Three runtime findings sharpen the implementation boundary:

1. A live coding workspace exists, but an ungranted bot returns `{"agents":[],"unavailable":[],"message":"No coding agents are assigned to this bot."}`. Discovery cannot be fixed by changing descriptions or grant defaults alone: the extension receives only a lookup function, not directory enumeration.
2. `PUT /v1/workspaces/coder-a` with model `faux-2` after registering `faux-1` returns HTTP 200 and still reports `faux-1`. This endpoint is idempotent registration, not an update operation. The pinned Pi Durable 1.2.0 package already exposes `Conversation.configure(change, context)` and `AgentChange.model`; use that seam rather than replacing the conversation. See installed `node_modules/@earendil-works/pi-durable/dist/harness/types.d.ts` lines 377–394 and 588–593; current model setup is in [workspace.ts lines 255–274](../packages/runner/src/workspace.ts).
3. Two `POST /goals` calls with the same `requestId` create different goal IDs. The HTTP goal-create path ignores that field and generates a new target-side record each time. The same concern applies to loop creation. A bot tool's source-side memo alone cannot close a crash between target commit and source acknowledgement: the target must deduplicate the operation. The existing bot prompt's stable `bot:<bot-id>:<tool-task-id>` input key is the useful precedent. [Goal/loop creation lines 380–387 and 422–468](../packages/runner/src/schedule.ts), [prompt lines 223–229](../packages/runner/src/bot.ts).

### Implementation shape after ticket consolidation

Keep TASK-36 as one user feature delivered in two reviewable behavior chunks. The initial suggestion of two TASK-36 subtickets is superseded by the final consolidation: shared lifecycle work is TASK-47, model reconfiguration is reused from TASK-38, and pod transport is TASK-22. Do not duplicate those implementations in new bot-specific services.

1. **Global discovery and conversation control.** All live coding agents, full paginated history/status, explicit input modes, resume/abort, and target goals/loops with replay receipts. Exercise direct tools and Code Mode. This can be developed against the existing faux-model fixture; do not mark the parent complete at this point.
2. **Durable workspace creation, configuration, and destruction for bots.** Consume TASK-47's lifecycle owner shared by CLI and bot entry points, using immutable IDs and durable operation outcomes, and TASK-38's model-change API. Preserve existing Rust ownership, failure phases, and tombstone guarantees. Avoid building a second TypeScript provisioner. A request replay after successful creation must return the original workspace, including after its name was reused, rather than create a replacement or fail ambiguously. Current CLI creation generates a new UUID for each request and treats an already-ready name as a conflict; it is not yet this operation API. [UUID creation line 208 and creation retries lines 493–519](../src/workspaces.rs).

Define the initial mutable configuration narrowly: model/provider, agent instructions, and runtime resources where supported; immutable workspace ID/role/storage identity stay immutable. Configuration should complete at a documented safe boundary, keep history, report the actual selected model, and surface missing authentication without switching provider. More mutable fields can follow concrete use cases; do not interpret “configure” as permission to silently replace a workspace's files or identity.

TASK-22 and this work need one shared directory/management transport contract. The current bot closure directly returns in-process objects, the runner accepts loopback binds only, and workspace NetworkPolicy disallows cross-namespace ingress and excludes Pod/service CIDRs on ordinary egress. A pod bot cannot simply call today's host loopback endpoint or another Pod. The management interface must carry the bot role's authorized lifecycle operations while ordinary coding workspaces retain isolation; cluster credentials do not need to enter bot tools. This routing contract is a real integration dependency; pod-runtime implementation does not need to block all local API/test work. [main.ts lines 33–45, 206–231](../packages/runner/src/main.ts), [NetworkPolicy line 419](../src/workspaces.rs).

Do not merge completed TASK-29: it deliberately implemented the older permission policy and remains useful historical evidence. TASK-36 is broader new work. Keep bot lifecycle authority distinct from filesystem access: it may prompt/control another agent through management APIs while each workspace keeps its own files.

## TASK-39: make own-container sudo the default

There is no current human-versus-agent account problem to solve. Human `kubectl exec` and agent remote execution both use the `dev` container's UID/GID 1000. The current image already installs `sudo` and `nano` and permits passwordless sudo for UID 1000. The blocking default is `allowPrivilegeEscalation:false` plus all capabilities dropped. Opt-in flips escalation and adds CHOWN, DAC_OVERRIDE, FOWNER, SETGID, SETUID. Bots currently receive only a namespace and no Pod. [Image lines 24–27](../image/Dockerfile), [manifest lines 393–419](../src/workspaces.rs), [agent exec lines 165–184](../packages/runner/src/kubernetes-env.ts).

Make own-container administration the standard profile for newly created workspaces and remove the opt-in requirement. Retaining UID 1000 for ordinary work while allowing unattended sudo keeps normal Git/file ownership usable. It does not require separate agent identities, approval prompts, host mounts, service-account token automount, or privileged mode. Ordinary container-root capabilities still need to support the requested administrative operations: the current five-cap profile's passing simple package fixture is evidence for that fixture, not a proof that every package hook or kernel operation works. Kubernetes documents the independent effects of [privilege escalation and capabilities](https://kubernetes.io/docs/tasks/configure-pod-container/security-context/) and [kernel security constraints](https://kubernetes.io/docs/concepts/security/linux-kernel-security-constraints/).

Implementation scope:

- Emit the standard administrative profile directly in the workspace Deployment and remove `--allow-sudo` and obsolete profile branches. The early-alpha design can replace its stored schema directly; no old-profile upgrade machinery is needed. The current profile fields and comparison live at [workspaces.rs lines 53–79 and 694–709](../src/workspaces.rs).
- Create fresh workspaces from an image that actually contains sudo and test it under the emitted security policy. The locally cached `adm-dev:0.1.0` is `6ab4c21052fe…` and has no sudo at all; cached `adm-dev:task-33` is `983387534c7a…` and does. This is local cache evidence, not a claim about currently running cluster images or an image-upgrade requirement.
- Keep creation retries, failure reporting, and ordinary Pod replacement correct for workspaces created by the new design. Repository files/Git and pod-owned agent history persist; package installations remain in the replaceable container. The init script assigns the persistent workspace to UID 1000 ([adm-init-workspace lines 10–13](../image/adm-init-workspace)).

Keep TASK-39 as one ticket covering the default for fresh workspaces. Apply it to bot containers as TASK-22 gives them Pods. Do not merge/reopen completed [TASK-33](https://linear.app/wylynko/issue/TASK-33): that change delivered the earlier editor/opt-in policy; TASK-39 supersedes its defaults. Update the operational contract, CLI help, AGENTS notes, and tests to describe the new standard profile.
