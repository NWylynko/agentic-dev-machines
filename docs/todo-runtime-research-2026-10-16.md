## Settled requirements

- Every agent harness, model request, coding tool, MCP subprocess, goal, and loop runs inside its workspace Pod. The management host provides access and routing only. An unavailable access host must not stop agent work.
- Agents control their own container/Pod, including root/sudo. Do not reintroduce per-command approvals or promise that credentials available in that trust boundary are inaccessible to its agent.
- Bots broadly control coding-agent lifecycles. The in-cluster management API must remain usable while the access host is offline.
- Infisical can remain an operator preference; it is not a product prerequisite. No secret values in repository environment files, ADM defaults, generated units, or logs.
- Nick's newer TASK-25 comment (2026-10-16 14:25 UTC) explicitly requests "the full pi interface, with the model selector specifically." This supersedes the earlier ticket's narrower terminal-enhancement scope. TASK-25 retains broader Pi-interface integration; TASK-38 owns working model selection. TASK-46 autocompletions is outside this Todo investigation.
- Early-alpha direction: start fresh with the new design. No migration, import, old-format compatibility, or preservation of existing host sessions/configuration is required. Ordinary persistence and restart correctness apply to workspaces created under the new design.

### Proposed implementation boundary

Reuse the HTTP/SSE transport and durable Workspace implementation where useful, running one workspace owner in that workspace's Pod. Breaking API/configuration changes are acceptable; old clients and stores need no compatibility layer. Package the pinned runtime and its production dependencies in the image using the same packaging constraints as releases: worker/WASM assets must survive. Start it as the supervised container process; runtime readiness must mean the matching durable store is open and API available, rather than just `/repos` existing.

For coding agents, use local `NodeExecutionEnv` rooted at the persisted workspace cwd. `environment: local` currently describes test configuration; introduce an explicit distinction between runtime location and tool transport rather than exposing "local" as a host-execution product option. Coding tools no longer need host kubeconfig references. Bots get Pod resources and private durable storage without installing coding tools or repository access. Configure MCP executable paths for the bot image directly; no host configuration import is required.

Provide authenticated in-cluster runtime/control transport and access-plane forwarding. A Service/port-forward design is a candidate, not an implemented fact. Loopback forwarding alone covers human access but does not let bots manage agents when the host is down. Do not merely permit `0.0.0.0` on the current unauthenticated API. Preserve stable workspace ID, request IDs, public/diagnostic history distinction, SSE cursors, abort semantics, and connection errors.

The current NetworkPolicy admits only same-namespace ingress and excludes Pod/Service CIDRs from ordinary egress; the Pod disables service-account-token automount ([manifest:418](../src/workspaces.rs#L418)). Add only the explicit in-cluster routes and identities the management contract needs. Coding agents retain their own-pod authority without inheriting cluster-admin credentials. Bot lifecycle calls need the shared in-cluster lifecycle owner identified by TASK-36/TASK-41; that owner must survive deleting a managed agent Pod. This work is separate from an agent harness and must not become host compute.

### Persistent state and ordinary restart recovery

Create each new workspace's conversation DB, profile, schedule/checkpoints, and runtime configuration directly on its private persistent volume, alongside its own files. Reopening that new-design store after ordinary process/Pod replacement must retain workspace identity, history, cursors, model selection, and saved work. Host stores are not imported or converted.

Keep one active owner of each new-design store, resume durable work on runtime startup without requiring an attached client, and retain request identities so retries do not duplicate completed effects. Intentional destruction cancels owned work and prevents recreation. These are current functionality requirements, not compatibility or migration work.

The existing exclusive transaction protects simultaneous local processes but local PID metadata is not cross-node fencing. RWO permits multiple Pods on one node; Recreate describes rollout order, not arbitrary failure recovery. [Kubernetes documents RWO versus RWOP](https://kubernetes.io/docs/concepts/storage/persistent-volumes/#access-modes). Test the chosen single-owner/fencing mechanism on the installed CSI/storage stack rather than claiming changing to RWOP alone proves node-loss safety.

The installed Durable contract requires one process per store ([Pi 1.2.0 README:665](../node_modules/@earendil-works/pi-durable/README.md#L665)). Its SQLite adapter uses WAL and synchronous NORMAL ([adapter:151](../node_modules/@earendil-works/pi-durable/dist/storage/sqlite/node.js#L151)); clean close checkpoints the WAL at line 133. [SQLite's WAL documentation](https://www.sqlite.org/wal.html) explains that live WAL state is part of the database and WAL is unsuitable for a shared network filesystem. Persist the new runtime's complete SQLite state on the chosen compatible volume.

Reopening a harness reconciles tasks, but arbitrary interrupted shell/MCP effects are not transparently resumed. The installed tool task records an interruption unless both persisted and current replay policy are safe ([tool.js:95](../node_modules/@earendil-works/pi-durable/dist/harness/tool.js#L95)). Preserve this instead of marking commands replay-safe to make restarts appear seamless. Sudden-node loss and its accepted loss window remain unmeasured; existing controlled Longhorn handoffs do not establish them.

## TASK-38: missing UI/API plus two persisted model authorities

### Reproduced behavior

An isolated real HTTP runner accepted a model-less bot and returned `needs_model`; input returned `409 MODEL_REQUIRED` with empty history. Repeating registration PUT with an explicit model still returned `needs_model`. `/model` returned 404. This reproduces the absence of a model-selection path without contacting a provider.

- [`src/workspaces.rs:487`](../src/workspaces.rs#L487) blocks ordinary creation without a model or `--no-agent`; line 586 skips registration entirely for shell-only workspaces. [`src/main.rs:916`](../src/main.rs#L916) applies configured defaults.
- [`runner/main.ts:551`](../packages/runner/src/main.ts#L551) creates a registration only if it is new; later PUTs return the previous Workspace. There is no model endpoint.
- [`workspace.ts:266`](../packages/runner/src/workspace.ts#L266) supplies the initial model to `harness.root()`. The installed [`harness.js:219`](../node_modules/@earendil-works/pi-durable/dist/harness/harness.js#L219) returns an existing root without applying new initialization options.
- [`workspace.ts:369`](../packages/runner/src/workspace.ts#L369) and line 396 use `config.model` for status/admission while Durable persists a separate agent model. Updating only JSON or only the root initialization cannot satisfy restart-safe selection.
- [`terminal.ts:326`](../packages/terminal/src/terminal.ts#L326) explicitly says `/model` is unavailable. The existing terminal component/PTY test seam exercises the real client. Nick has now explicitly requested the full Pi interface in TASK-25; the concrete selector-reuse seam below advances that request without starting another agent owner.

The installed Durable API already exposes `conversation.configure({model: {provider, modelId}}, context)` ([types:591](../node_modules/@earendil-works/pi-durable/dist/harness/types.d.ts#L591)). A local SQLite probe configured a model, closed/reopened the harness, and confirmed it persisted on the same conversation ID; passing a different model to root initialization on reopen did not replace it.

### Implementation shape and tests first

Keep this one user feature. Always register the default agent and remove `--no-agent`; allow `needs_model` to be a valid ready workspace. Add a catalog/auth-metadata endpoint and serialized model-change endpoint owned by the workspace runtime, then add a terminal picker and later `/model` selection. Reuse that model-change operation for TASK-36's bot control; do not build a second path.

Reuse the exported Pi `ModelSelectorComponent` rather than inventing a selector. The installed public exports include both the component and `initTheme` ([index.d.ts:35](../node_modules/@earendil-works/pi-coding-agent/dist/index.d.ts#L35)). The constructor's concrete ModelRuntime type requires a deliberate adapter boundary or an upstream interface extraction, not a fabricated full session implementation.

A `/tmp` probe instantiated that actual Pi component with a synthetic catalog facade and initialized theme, rendered it, searched for `beta`, and selected it with Enter; it requested one catalog refresh and created no AgentSession or provider request. In production its select callback should call the durable model-change endpoint and show any persistence/auth error. Native [`InteractiveMode.showModelSelector:4448`](../node_modules/@earendil-works/pi-coding-agent/dist/modes/interactive/interactive-mode.js#L4448) delegates selection to `session.setModel`; ADM should substitute its remote operation. Use the persisted Durable agent model as the canonical selected model. Registration/defaults seed new agents; re-registration must preserve a terminal choice. Avoid separate uncoordinated writes to `workspaces.json` and `pi.agent`. Validate the selected chat model against the actual configured runtime catalog; display missing authentication as actionable metadata/error without silently choosing another provider. Define when a busy agent applies a model change (a request already prepared keeps its model; Pi documents changes take effect on the next request), and test that boundary.

## TASK-42: provider-neutral fresh credential setup for Pods

### Source and isolated evidence

[`models.ts:10`](../packages/runner/src/models.ts#L10) creates Pi ModelRuntime, optionally with `authPath`; no Infisical SDK/client is in this path. The product's hard requirement currently occurs in setup messaging ([`src/setup.rs:281`](../src/setup.rs#L281)), [schema comment](../.env.schema#L2), installation/operations guidance, and project guidance. [`setup.rs:330`](../src/setup.rs#L330) launches pinned native Pi for `/login`, writing its ordinary host auth store. Generated systemd units at line 255 inherit a PATH but no login-shell provider keys. Rewording docs is independently useful, but the post-TASK-22 credential path cannot remain host-only.

In a clean child environment with explicit in-memory CredentialStore, `modelsPath: null`, `refreshOnCreate: false`, no ambient HOME override, and only OpenAI availability queried, Pi listed 44 static OpenAI chat models, zero available models without auth, and 44 available models after a synthetic process-environment key. No default auth/config/cache path was used. This establishes provider-neutral environment injection and catalog availability, not validity of a real credential or an account's subscription compatibility.

Pi supports an injected `CredentialStore` or file-backed `authPath`; its storage API includes read/list/modify/delete ([ModelRuntime options:4](../node_modules/@earendil-works/pi-coding-agent/dist/core/model-runtime.d.ts#L4), [AuthStorage:376](../node_modules/@earendil-works/pi-coding-agent/dist/core/auth-storage.js#L376)). File storage takes a cross-process lock and persists mutations ([AuthStorage:123](../node_modules/@earendil-works/pi-coding-agent/dist/core/auth-storage.js#L123)). A read-only mounted auth.json is not a complete OAuth lifecycle because refresh/logout need writes; the provided read-only store explicitly rejects them at line 234.

OAuth needs one canonical mutable refresh owner per intentionally shared credential/token family. Separate logins for the same account may produce independent token families. Pi refreshes near-expiry credentials under `CredentialStore.modify` and commits rotated tokens before releasing its lock ([auth/resolve.js:46](../node_modules/@earendil-works/pi-ai/dist/auth/resolve.js#L46)). A synthetic rotation probe made two concurrent calls against one shared store and observed **one refresh**. Copying the same starting credential into two independent stores made **two refresh attempts**, with the second failing after the first consumed its single-use refresh token. This demonstrates the design hazard; it does not assert every provider uses single-use refresh tokens.

Stored credentials own provider auth resolution: failed OAuth refresh does not silently switch to an environment key ([resolve.js:5](../node_modules/@earendil-works/pi-ai/dist/auth/resolve.js#L5)). Preserve that useful property.

### Implementation contract and test order

Keep TASK-42 separate from TASK-38. Support the operator's chosen injection mechanism, document Pi login, and keep application schema/config free of secret values. Under the settled pod architecture, define an explicit per-workspace credential reference/delivery contract and make "how it reaches the Pod after restart" concrete. Environment injection, a mounted provider store, or an external-store adapter are mechanisms; no new secret manager is mandatory. Credential material must not be routed through normal status/history/registration payloads or generated service units.

Configure credentials fresh for the target design: per-workspace login or operator-chosen injection into its Pod. Do not copy or migrate existing host auth stores. API keys can be scoped/injected per Pod using an operator-managed source; fresh OAuth login needs a writable store that persists its refresh/logout state. Independent workspace logins can avoid coupling token families. If a token family is deliberately shared, its refresh/revocation must be synchronized; that correctness constraint does not require adding a generic credential broker or another mandatory service. A host dependency for credential refresh would violate access-plane independence.

Full own-pod root means an agent may access credentials actually delivered to that Pod. Do not promise environment/file redaction isolates them from the same agent. Scope delivery to the selected workspace/provider, avoid exposing other workspaces' or management/cluster credentials, and ensure any bot management identity grants only its intended management API. Root privileges are not grounds to reintroduce approval prompts.

Test first with no Infisical executable/configuration, explicit synthetic auth/config/models/cache paths or in-memory stores, a fake service boundary, and synthetic credentials; preserve or omit HOME rather than repurposing it. Verify setup/login paths and chosen pod injection independently of the interactive shell; restart the runtime and model catalog/auth status; assert absent credentials fail visibly. Then fake OAuth expiry, concurrent refresh, refresh-token rotation, cancellation after rotation, runtime restart, logout/revocation, and failed refresh without fallback. Scan fixture logs/config/unit/metadata/history for the synthetic sentinel; do not scan or print live credentials. Preserve existing explicit MCP `inheritEnv: false` and secret-reference grants when moving MCP into Pods.

Dependencies: agree the TASK-22 runtime/credential reference contract first. TASK-42 supplies fresh login/injection and credential lifecycle for new Pod runtimes. Generic wording and no-Infisical setup coverage can land independently; fresh credentials reaching Pods and surviving ordinary runtime restart must be proven before declaring runtime integration complete. There is no host-auth import or old-format preservation obligation.
