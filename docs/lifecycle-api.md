# In-cluster lifecycle API

`adm lifecycle-serve` is the single owner of workspace creation, identity, and destruction. It runs in a dedicated control namespace with a persistent volume for its SQLite journal and is exposed through a cluster Service. The management host is a client; it does not own lifecycle metadata or cleanup workers.

Every route except `GET /health` requires `Authorization: Bearer <token>`. The service reads the token from a mounted Secret file supplied through `--lifecycle-token-file`; CLI clients use the same file through `--lifecycle-token-file` or `ADM_LIFECYCLE_TOKEN_FILE`. The current service has one shared bearer token with full lifecycle API access. Keep the ClusterIP Service private; do not give this token to workspace Pods or expose the service without authenticated transport. Only the token-file path is CLI configuration. The token itself is never stored in workspace specs, operation receipts, or logs. TASK-22 owns runtime-specific authenticated routing and permissions.

Every caller supplies a stable `operationId` (UUID) for replay. A successful admission writes the normalized request, immutable workspace ID, and `accepted` receipt before returning HTTP 202. Repeating the same operation ID and creation intent returns the same receipt and allocated identity. Reusing an operation ID with a different request returns HTTP 409. Create accepts only caller choices; it rejects unknown fields and allocates the immutable workspace ID, namespace, creation time, and `provisioning` phase during admission. Delete addresses only an immutable ID. Human names are unique while live and can be reused after deletion without changing old receipts.

## Routes

- `POST /v1/operations` with `{operationId,kind:"create",spec:{name,role,image,storage_class,storage_size,cpu,memory,agent_enabled,allow_node_local_storage,repositories,catalog,repository,cwd,model,credential_env,allowed_agents,mcp_servers,herdr_space}}` or `{operationId,kind:"delete",workspaceId}`. Create `spec` contains creation choices only; identity and lifecycle fields are rejected. `credential_env` carries only `{name,secret_name,key}` references to a Secret in that workspace namespace; no secret values are accepted. Returns `{operationId,kind,status,workspaceId,acceptedAt,updatedAt,stage,lastError,timings,fencingToken}` and HTTP 202 after durable admission.
- `GET /v1/operations/{operationId}` returns that durable receipt; unknown operation IDs return 404.
- `GET /v1/workspaces` returns the canonical directory, indexed by immutable workspace ID, with a single bounded Kubernetes Pod list joined by the recorded namespace and immutable workspace label. Each live workspace has `runtime_status` with `podName`, `nodeName`, `podPhase`, `ready`, optional `containerReason` and `error`; list failure is included as an unavailable cause. A missing or duplicate owned Pod remains explicit.
- `GET /v1/workspaces/{workspaceId}` returns the service-owned workspace record and current lifecycle/runtime routing status, including the creation operation ID; unknown IDs return 404.
- `POST /v1/workspaces/{workspaceId}/runtime/lease` with `{holder:<pod-uid>}` issues the active Pod a 30-second workspace fence. `/runtime/lease/renew` accepts `{holder,fencingToken}` and `/runtime/check` validates the same pair. These routes require the workspace Pod's projected ServiceAccount token with the dedicated `adm-lifecycle` audience. The service validates the TokenReview username against `system:serviceaccount:<canonical-namespace>:adm-runtime` and its bound Pod UID against `holder`; a Pod cannot act for another workspace. The general lifecycle bearer token is not accepted for these routes. A deleting/deleted workspace returns 410; wrong workspace identity or fence returns 403.
- `POST /v1/workspaces/{workspaceId}/runtime/authorize` accepts `{action}` where action is `read`, `prompt`, `abort`, `resume`, `goal`, `loop`, `model`, or `delete`. A workspace runtime may act on itself; a canonical bot runtime may authorize a cross-workspace call, leaving its explicit target grant check to the runtime; the lifecycle ServiceAccount may authorize only cleanup actions `delete` and `abort`. The target must be live, except lifecycle cleanup; callers are identified by audience-scoped TokenReview, not by copying another workspace's token.
- `GET /health` reports service and journal readiness.

Create/delete completion is performed by a restartable worker in this service. The operation row and workspace row are committed before work begins; current stage, elapsed timing, and errors are persisted. Deletion admission changes the workspace to `deleting` before cleanup. The service verifies both ownership labels and the immutable ID before deleting the namespace. A missing namespace completes against the canonical directory record. Failures remain visible on the receipt and are retried by explicit replay or service reconciliation.

The service uses one active owner, guarded by a Kubernetes Lease updated with resourceVersion compare-and-swap. A monotonically increasing fencing token is recorded with operation and workspace updates; the worker checks the Lease before and after every Kubernetes command. Each workspace runtime also has its own durable 30-second lease in the directory store. The runtime must call `/runtime/check` at its new-work admission and Durable commit boundaries; `deleting` rejects new checks immediately, including while the serialized cleanup worker is busy on another operation. The process-boundary contract test covers denial after deletion admission while cleanup is queued behind another deletion; runtime Durable commit-hook coverage belongs to TASK-22. The persistent volume stores state; it does not establish ownership by itself. A replacement service must acquire the expired lifecycle Lease before reconciling the durable queue.

CLI create and destroy submit an operation and poll its durable receipt until completion, then return the canonical workspace record. Create records its creation operation ID in that record so an operator can replay the same failed operation with `--operation-id`. List, status, and inspect also use the service-owned directory; Herdr close handling submits the same delete operation. Bot lifecycle callers use the same API contract. The runtime directory is addressed by immutable ID so pod runtimes can register and route without treating a human name as identity. Runtime model changes remain a separate runtime configuration operation.

## Fresh control-plane install

The control-plane Deployment uses the published ADM workspace image, which contains the `adm` binary and pinned `kubectl` binary. First create `adm-system` and a client bearer-token file with restrictive permissions, then store the same value in Kubernetes Secret `adm-lifecycle-token` under key `token`. Do not put its value in a manifest, shell history, or normal ADM config. Apply `deploy/lifecycle/control-plane.yaml`; it installs the service account/RBAC, token-file mount, Lease owner, `adm-replicated` persistent claim, one-owner Deployment, and private ClusterIP Service. The cluster must already have the `adm-replicated` StorageClass.

The management host can forward the private Service with `kubectl -n adm-system port-forward service/adm-lifecycle 7433:7433`. Supervise that tunnel as part of the management-host access plane. Point clients at `http://127.0.0.1:7433` using `ADM_LIFECYCLE_URL`, and point `ADM_LIFECYCLE_TOKEN_FILE` at the protected client copy. Keep the token file outside the repository and readable only by the client account. The control-plane Deployment should use the matching published image for the installed CLI release. This is a deployment recipe, not a live-cluster validation claim.
